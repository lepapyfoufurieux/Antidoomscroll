Architecture du code d'Antiscrolling

Comment organiser le code pour couvrir toutes les fonctionnalités retenues : blocage, frictions, statistiques et motivation, sans réécriture entre le MVP et la version complète, et publiable sur le Play Store.

Choix de base

Principes

Une décision, un seul endroit

Toutes les règles (quota, horaires, focus, frictions) sont évaluées par une fonction Kotlin pure, RuleEngine.decide(). Elle ne dépend pas d'Android, donc elle se teste en JUnit simple.

Android mesure, on ne duplique pas

Le temps passé et les déverrouillages viennent de UsageStatsManager. On ne stocke que ce qu'Android ne garde pas longtemps : un résumé par jour, rattrapé au démarrage du service.

Tout en mémoire

Le service lit les règles et les accès temporaires en mémoire (StateFlow). Aucune requête en base ni dans UsageStats à chaque changement d'appli. Les écritures en base suivent, en arrière-plan.

Pas de framework en trop

Un seul module Gradle, une injection de dépendances manuelle (AppContainer), ni WorkManager ni DataStore. Hilt ou le multi-module pourront venir si l'appli grossit.

Rien ne quitte le téléphone

Pas de permission INTERNET, et allowBackup="false" pour éviter la sauvegarde Google Drive. Les données restent sur l'appareil, ce qui simplifie la déclaration d'accessibilité et le formulaire « Sécurité des données » du Play Store.

Le cœur

Le moteur de règles

Une seule fonction reçoit tout ce dont elle a besoin et rend une décision. Les règles sont vérifiées dans un ordre fixe : la première qui s'applique gagne.

sealed interface Decision {
    data object Allow : Decision
    data class Block(val reason: Reason) : Decision          // FOCUS, SCHEDULE, QUOTA
    data class Friction(val delaySec: Int, val steps: List<Step>) : Decision
}

data class Context(
    val usedTodayMs: Long,        // début de session (UsageCalculator) + temps écoulé
    val grantUntil: Instant?,     // accès temporaire « 5 min », lu en mémoire
    val focus: FocusSession?,     // dernière session lancée, active ou non
    val opensToday: Int = 0,      // ouvertures accordées aujourd'hui (open_event), pour le délai croissant
)

fun decide(rule: Rule?, now: ZonedDateTime, ctx: Context): Decision = when {
    rule == null || !rule.enabled                        -> Decision.Allow
    ctx.focus?.isActive(now) == true                   -> Decision.Block(Reason.FOCUS)
    rule.schedules.any { it.contains(now) }             -> Decision.Block(Reason.SCHEDULE)
    rule.quotaReached(ctx.usedTodayMs)                  -> Decision.Block(Reason.QUOTA)
    ctx.grantUntil?.isAfter(now.toInstant()) == true     -> Decision.Allow   // un accès ne lève que la friction
    else                                                -> rule.friction(ctx.opensToday)   // Allow si aucune friction
}

Les blocages durs (focus, plage horaire, quota) passent avant l'accès temporaire : choisir « 30 min » à 21h58 ne traverse pas la plage de 22h, et un accès ne dépasse jamais le quota. now est un ZonedDateTime pour que minuit et les changements d'heure soient justes.

Les profils choisissent les règles avant le moteur. Chaque profil a ses propres réglages par appli et des horaires où il est actif. RuleSet.at(now) rend les règles du profil actif : le plus ancien profil activé dont un horaire contient now (ou activé sans horaire : il s'applique tout le temps), sinon le profil « Par défaut », qui n'a pas d'horaire et s'applique le reste du temps. decide() ne connaît pas les profils. Le focus reste commun à tous les profils, et le temps du jour compte pour l'appli, quel que soit le profil. Un nouveau profil copie les réglages du profil par défaut.

Le délai croissant se calcule dans Rule.friction(opensToday) : délai de base + ouvertures du jour × incrément, plafonné à 2 min (ou au délai de base s'il est plus long). Les étapes (Step) sont la liste ordonnée des frictions activées pour l'appli : attente, question d'intention, petite tâche, choix de durée.

Les réglages simples (onboarding terminé, appli affichée dans le widget, consentement donné) vont dans SharedPreferences. Tout le reste est dans Room.

Le temps du jour se calcule dans UsageCalculator, une fonction pure qui reçoit les événements ACTIVITY_RESUMED / ACTIVITY_PAUSED de queryEvents(), plus précis que les totaux agrégés. Elle gère les applis à plusieurs activités, un PAUSED manquant, une session commencée avant minuit et une appli encore ouverte. Les déverrouillages viennent des événements KEYGUARD_HIDDEN, d'où le minSdk 28.

Migrations. Avant la première publication, effacer la base à chaque changement de schéma suffit. Après, chaque changement de schéma a sa migration Room, avec exportSchema activé, pour ne pas perdre l'historique des utilisateurs.

Onboarding

Permissions à obtenir

Aucune ne s'accorde par une simple boîte de dialogue, sauf les notifications. L'onboarding ouvre le bon écran des paramètres et vérifie au retour.

Obligatoire

Écran d'information et consentement

Avant Paramètres › Accessibilité : ce qui est lu (le nom de l'appli ouverte), à quoi ça sert, rien ne quitte le téléphone. Validé par un bouton « J'accepte ». Exigé par Google Play.

Obligatoire

Service d'accessibilité

Détecter l'appli ouverte. Paramètres › Accessibilité.

Obligatoire

Accès aux données d'usage

PACKAGE_USAGE_STATS, pour le temps et les quotas.

Obligatoire

Liste des applis installées

<queries> sur les intents MAIN/LAUNCHER et MAIN/HOME dans le manifeste. Sans HOME, le lanceur est invisible et le retour à l'accueil passe inaperçu.

Optionnel

Accès aux notifications

Uniquement pour masquer les notifications. Ne lit que le package de la notification. Comme l'accessibilité, grisé pour une appli installée hors Play Store (paramètres restreints).

Optionnel

Envoi de notifications

POST_NOTIFICATIONS (Android 13+), pour l'alerte avant la limite.

Recommandé

Pas d'optimisation de batterie

Évite que certains fabricants coupent le service. Ouvre la liste des réglages (ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS), pas la demande directe que Play réserve à certains usages.

Exclue

Internet

Pas de permission INTERNET : aucune donnée ne quitte le téléphone.

À prévoir dès le début

Points délicats

Fenêtres parasites

Clavier, barre de notifications, dialogues et l'appli elle-même déclenchent aussi des événements. Le service ne garde que ceux dont className est une vraie Activity (getActivityInfo réussit), et ignore son propre package et le lanceur, trouvé avec resolveActivity sur l'intent HOME.

Boucle de blocage

Quand BlockActivity se ferme, l'appli revient et redéclenche un événement. L'accès temporaire est écrit en mémoire avant finish(), puis en base en arrière-plan. Attendre que Room émette de nouveau laisserait passer l'événement et rebloquerait l'appli.

Démarrage à froid

Quand Android relance le processus, les règles ne sont pas encore chargées. Le StateFlow commence à null (« pas chargé ») et le service attend le chargement avant sa première décision, sinon tout serait autorisé.

Temps qui expire dans l'appli

Rester dans une appli ne génère aucun événement. Le QuotaWatcher rappelle decide() toutes les 15 s : fin d'accès, quota, plage horaire et focus sont pris en compte sans calculer d'échéance à part, et sans dépendre de delay(), qui se met en pause écran éteint.

Changement de jour

Quotas et délai croissant repartent à zéro à minuit. Le moteur reçoit now en ZonedDateTime, ce qui rend minuit et les changements d'heure faciles à tester.

Fabricants agressifs

Xiaomi, Huawei, Samsung peuvent tuer le service. L'écran d'accueil affiche un avertissement si le service n'est plus actif.

Notifications déjà affichées

NotificationBlockerService met en attente les notifications qui arrivent pendant un blocage, pas celles déjà dans le volet quand il commence. Les notifications en cours (musique, appel) ne sont jamais touchées.

Contournements

Image dans l'image, écran partagé, version web dans Chrome, service désactivé dans les paramètres : non bloqués pour l'instant. Piste : enregistrer les périodes où le service était coupé et les afficher dans les stats.

Distribution

Publication sur le Play Store

Le plus gros risque du projet n'est pas dans le code : c'est l'acceptation du service d'accessibilité par Google.

Risque principal

Déclaration d'accessibilité

Antiscrolling n'est pas un outil d'accessibilité au sens de Google. Formulaire de la Play Console : pourquoi l'API est utilisée, données collectées (aucune), vidéo de l'écran d'information. Argument : UsageStats ne permet ni de réagir à l'ouverture ni d'afficher l'écran de blocage par-dessus l'appli.

Règles fixées par l'utilisateur

La politique autorise l'automatisation à base de règles définies par l'utilisateur et interdit les actions autonomes. Le moteur de règles reste dans ce cadre : aucun blocage décidé par l'appli elle-même.

Sécurité des données

Sans permission INTERNET, le formulaire déclare « aucune donnée collectée ni partagée ». Une page de politique de confidentialité en ligne reste obligatoire.

Test fermé avant publication

Un compte développeur personnel récent doit faire tester l'appli en test fermé (12 testeurs pendant 14 jours, à vérifier dans la Play Console) avant la mise en production.

Plan B si refus

Détecter l'appli ouverte en interrogeant UsageStats à intervalles réguliers. Demande un foreground service et SYSTEM_ALERT_WINDOW, donc d'autres déclarations. Seule la détection serait à refaire, RuleEngine reste tel quel. Rien n'est construit d'avance.

Conséquence sur le planning. La version de l'étape 1 part en test fermé dès qu'elle tourne, pour savoir si l'accessibilité est acceptée avant d'écrire les statistiques et le widget.

Feuille de route

Ordre d'implémentation

Chaque étape produit une appli utilisable et s'appuie sur la précédente.

  1. Squelette et blocage simple MVP

    AppContainer, Room avec la table rule, onboarding avec écran d'information et consentement, choix des applis, service d'accessibilité, BlockActivity avec délai et bouton « 5 min » (accès en mémoire + table grant), premier QuotaWatcher. Envoi en test fermé pour faire examiner la déclaration d'accessibilité.

  2. Temps du jour et historique MVP

    UsageCalculator, UsageRepository, écran d'accueil avec le temps par appli. HistoryBackfill dès maintenant : Android ne garde le détail que quelques jours, ce qui n'est pas recopié est perdu.

  3. Quotas et alertes

    Règle de quota dans le moteur, notification « 5 min restantes ».

  4. Plages horaires et mode focus

    Tables schedule et focus_session, écrans associés.

  5. Frictions avancées

    Question d'intention, petite tâche, choix de durée, délai croissant via open_event.

  6. Statistiques

    Séries, résumé hebdo, nombre de déverrouillages, sur l'historique enregistré depuis l'étape 2.

  7. Widget et notifications masquées

    TimeLeftWidget et NotificationBlockerService.

  8. Profils

    Tables profile et profile_schedule, RuleSet, onglet Profils, choix du profil dans Applis.

Tests. Politique complète dans tests.md : JUnit pour domain/ et pour la colle (QuotaWatcher, repositories) avec des faux, recette écrite sur téléphone (recette.md) pour les services et les écrans. Chaque étape ajoute ses tests et ses scénarios de recette avant d'être terminée.
